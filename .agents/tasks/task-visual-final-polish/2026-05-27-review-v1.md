# Visual final polish: spacing, theming, cohesion, and mobile responsive layer

A single 503-line CSS addition (sections 4-8 of `visual-final-polish.css`) unifies spacing rhythm, dark/light theme token usage, component visual cohesion, and mobile responsive behavior across the platform. The file loads last in the import chain, relying on cascade order (not specificity escalation) for most desktop rules, but switching to `!important` for all mobile overrides. The approach is sound for a polish pass that can't refactor earlier layers — it acts as a correction sheet rather than a rewrite.

**Watch for:** Conflicting card padding at 480px between this file (`--sp-3`) and `responsive.css` (`--sp-4`) — both use `!important`, last-loaded wins, so the card will be tighter than the earlier layer intended (confirmed). The `:root .card` selector in Section 5 applies dark-mode surface/border to *all* cards regardless of theme, which may override light-mode card styling unless the `[data-theme='light'] .card` rule in Section 6 always wins specificity (confirmed — it does win by attribute selector, but the mental model is fragile). The sidebar RTL fix forces `inset-inline-end: 0` at 900px without checking whether the sidebar is already positioned correctly via `right: 0` in base.css, creating a no-op for LTR but potentially double-positioning in future refactors (likely).

## High-level view

Sections 4 through 7 standardize desktop-level appearance: consistent padding/gap values using the 8px grid, token-only backgrounds/borders for both themes, and unified border-radii plus hover transitions for all card-like elements. The approach replaces raw hex or rgba values in dark mode with `color-mix()` expressions and CSS custom properties, which is a genuine improvement for maintainability. However, it also *re-declares* the same background/border/radius values that `components.css` already sets for `.card`, so any future change to card appearance now requires updating two files.

Section 8 handles responsive and mobile concerns: tablet sidebar capping, mobile layout stacking with grid-template overrides, touch target enforcement via `pointer: coarse`, scroll-snap for filter bars and tables, RTL-aware positioning for the sidebar and metric icons, and `prefers-reduced-motion` disabling of transitions. The mobile section relies heavily on `!important` to override earlier responsive rules — this is defensible given the late-loading strategy, but creates a specificity ceiling that makes future overrides nearly impossible without `!important` escalation in consuming code.

## `:root .card` specificity trap

In Section 5, the selector group is:

```css
[data-theme='dark'] .card,
:root .card {
  background: var(--surface-1);
  border-color: var(--border);
}
```

The `:root .card` part matches every `.card` in the document regardless of theme, because `:root` matches `<html>`. The reason this doesn't visibly break light mode is that Section 6's `[data-theme='light'] .card` rule has equal specificity (0,1,1 vs 0,1,1) but loads *later* in the same file. If anyone reorders sections or adds another `.card` rule between them, light mode cards will inherit dark-surface values. The safer approach: remove `:root .card` entirely. The dark theme is already the default in this design system's token setup.

## Card padding conflict at 480px

`responsive.css` (loaded 14th in the import chain) sets:

```css
@media (max-width: 480px) {
  .card { padding: var(--sp-4) !important; border-radius: var(--r-lg) !important; }
}
```

This file (loaded last) sets:

```css
@media (max-width: 480px) {
  .card { padding: var(--sp-3) !important; }
}
```

Both use `!important`, both have identical specificity (0,1,0 inside the same media query). Last-loaded wins. The card padding on small phones is now `--sp-3` (12px) instead of `--sp-4` (16px). Additionally, `responsive.css` also forces `border-radius: var(--r-lg) !important` at 480px, which contradicts Section 7's `border-radius: var(--r-2xl)` (no `!important`). So on small phones, cards get 12px radius from `responsive.css` and 12px padding from this file — an unintentional visual mismatch from the desktop style where both values are larger.

Similarly, `responsive.css` sets `.auth-glass-card { padding: var(--sp-5) !important }` at 480px, while this file sets `.auth-glass-card { padding: var(--sp-4) !important }` — again, last-loaded wins. These should be reconciled.

## Component visual cohesion: hover state broadening

Section 7 introduces a unified hover pattern for interactive cards:

```css
.card.bordered:hover,
.card.interactive:hover,
.thumb-card:hover,
.track-card:hover,
.webinar-card:hover,
.exam-row:not(:disabled):hover {
  transform: translateY(-2px);
  box-shadow: var(--shadow-card-hover);
  border-color: color-mix(in srgb, var(--accent) 20%, var(--border));
}
```

`components.css` already defined `.card.bordered:hover` with `translateY(-1px)` and `--shadow-md`. This file bumps it to `-2px` and `--shadow-card-hover`, which is a stronger elevation. The change is intentional (polish pass), but note that the `color-mix()` uses 20% accent vs the original's 30% accent — the hover border is now *subtler* while the lift is *more aggressive*. Whether that's desired or an oversight depends on design intent.

## Mobile `!important` saturation

Section 8 uses `!important` on 35 declarations. Combined with `stitch-canonical.css` (161 uses) and existing responsive layers, the specificity landscape is heavily overloaded. The `prefers-reduced-motion` block at the end correctly uses `!important` on `transition: none` to override the Section 7 transitions — but any future animation added without `!important` will be invisible under reduced motion. The reduced-motion block should probably target `*` or use a broader selector to be future-proof, though that's a design preference.

## RTL sidebar positioning

base.css positions the mobile sidebar with:
```css
@media (max-width: 900px) {
  .sidebar { position: fixed; right: 0; ... transform: translateX(100%); }
}
```

This file adds at the same breakpoint:
```css
.sidebar { inset-inline-end: 0; inset-inline-start: auto; }
```

For an RTL document (`dir="rtl"`), `inset-inline-end` resolves to `left` and `inset-inline-start` resolves to `right`. But base.css hardcodes `right: 0`. The physical property `right` and the logical property `inset-inline-end` can coexist in unexpected ways: when `right: 0` is set and `inset-inline-end` (resolving to `left`) is also set to `0`, both `right` and `left` become `0`, stretching the sidebar full-width in RTL. Whether this actually triggers depends on the specifics of how inset shorthand resolves with `width` constraints, but it's worth testing. The `transform: translateX(100%)` will still hide it off-screen, but the open state might render wider than expected.

## Reduced motion coverage

The `prefers-reduced-motion` block covers `.card, .metric, .btn, .thumb-card, .track-card, .webinar-card, .exam-row`. Missing from this list: `.badge-tile, .lesson-row, .leaderboard-row, .list-row` (which received `border-radius` from Section 7 and could inherit transitions from earlier layers), and any `.landing-*` elements that use CSS transitions for scroll-triggered animations. If the design system grows, this allowlist approach will silently miss new components.
