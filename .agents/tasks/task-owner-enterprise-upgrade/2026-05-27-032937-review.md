# Enterprise owner command center: realtime monitoring, AI telemetry, alerts, governance

The owner panel expands from basic user/activity management into a platform operations center with five new Prisma models (PlatformSetting, FeatureFlag, AiTelemetry, OperationalAlert, LoginEvent), ten new backend endpoints, ten new frontend hooks, four new pages, and upgrades to three existing pages. The approach layers an enterprise monitoring surface on top of the existing OWNER role infrastructure — same auth middleware, same route file, same hook patterns. Security posture improves with self-demotion and OWNER-promotion guards added to the role-change endpoint.

**Watch for:** Backend-frontend API contract mismatches across four endpoints where response field names diverge (confirmed). `groupBy(['createdAt'])` producing per-row groups instead of daily aggregates for trend/timeline data (confirmed). Missing `newUsersThisMonth` field in governance response (confirmed).

## High-level view

The backend endpoints follow the project's established patterns but the response shapes they produce don't match what the frontend hooks expect to consume. This contract gap will manifest as broken pages once real API data flows — the fallback demo data pattern masks it until then.

Three endpoints use `prisma.*.groupBy({ by: ['createdAt'] })` intending daily or weekly aggregates, but Prisma groups by the full timestamp (millisecond precision), producing one group per record instead of time-bucketed aggregates.

The frontend pages are self-contained with meaningful fallback data and will render something before the backend is wired. The critical problem is that four of the ten new hooks will receive response objects with different field names than their TypeScript interfaces declare, causing silent `undefined` values at runtime.

## Backend-frontend contract gap across the new endpoints

Four of the ten new endpoints return response objects whose field names and shapes diverge from the frontend TypeScript interfaces. Because the frontend falls back to hardcoded demo data via `?? FALLBACK_DATA`, these mismatches won't crash pages — they'll silently show stale demo values instead of live numbers.

```
// Backend /owner/realtime returns:
{ liveNow, recentAiMessages, activeSessions, examsInProgress }

// Frontend RealtimeMetrics expects:
{ activeSessions, aiRequestsPerMin, liveBroadcasts, activeExams }
```

Only `activeSessions` overlaps. The other three metrics will be `undefined`, triggering the fallback.

```
// Backend /owner/ai-metrics byFeature (raw groupBy):
[{ feature: "chat", _count: { _all: 5200 }, _sum: { inputTokens: ..., outputTokens: ... }, _avg: { latencyMs: ... } }]

// Frontend AiMetrics.byFeature expects:
[{ feature: "chat", count: 5200, tokens: 1800000 }]
```

The `Bar` chart in `OwnerAiPage` maps `f.count` and `f.tokens` — both `undefined` on the real response, producing empty charts.

The fix: add a transformation layer in each backend endpoint that maps the Prisma response into the shape the frontend expects. Backend transformation is preferable because it keeps the API contract explicit and decoupled from ORM internals.

## Timestamp-based groupBy producing useless aggregates

Three endpoints use `prisma.*.groupBy({ by: ['createdAt'] })` intending to produce daily or weekly aggregates. Prisma's `groupBy` on a `DateTime` field groups by the exact timestamp (millisecond precision), so each row becomes its own group.

Affected endpoints:
- `/owner/ai-metrics` trend (intended: daily request count for 7 days)
- `/owner/login-analytics` dailyBreakdown (intended: daily login counts for 30 days)
- `/owner/governance` newUsersByWeek (intended: weekly registration count for 8 weeks)

Fix with `$queryRaw` using `DATE_TRUNC('day', "createdAt")` as the grouping expression, or fetch records and bucket them in application code.

## Missing `newUsersThisMonth` in governance response

The frontend `GovernanceMetrics` interface expects `newUsersThisMonth: number`, rendered in a `MetricCard` on `OwnerGovernancePage`. The backend governance endpoint doesn't compute or return this field — it only returns `recentPermissions`, `recentRoleChanges`, and `newUsersByWeek`. The page will perpetually show the fallback value (156).

## Settings save batching in OwnerSystemPage

`handleSaveSettings` fires one `updateSetting.mutate()` call per changed key in a loop. Each mutation independently invalidates the `['owner', 'settings']` query on success. With multiple settings changed, the cache is invalidated and refetched N times in rapid succession, causing visible flicker. A batch endpoint or deferred invalidation would prevent this.

## OwnerRealtimePage status always shows "normal"

The live status bar always displays "النظام يعمل بشكل طبيعي" regardless of metrics or alert state. The `.has-alerts` CSS variant exists and is correctly used on the Dashboard page, but the Realtime page never applies it. The monitoring page is the one place where conditional status would matter most.
