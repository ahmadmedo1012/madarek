# Oasis widget de-distortion, bottom-nav scroll hide, and token cleanup

The Oasis chat widget panel was pinned to a fixed 500px height in world-class.css that visual-final-polish.css (loaded later, but with the same specificity) never overrode, causing layout distortion. This change removes the fixed height in favor of `height: auto`, softens a heavy teal glow in global-icon.css, replaces ~30 raw hex fallback values in world-class.css Section 10 with design tokens, and adds a hide-on-scroll behavior for the mobile bottom navigation bar via scroll-direction tracking in AppShell.tsx.

**Watch for:** Bottom nav stays hidden after route navigation if the user scrolled down on the previous page (confirmed). The `prefers-reduced-motion` block in Section 11 still applies `translateY(100%)` when reduced motion is active, which means the nav disappears instantly rather than remaining visible, an arguably worse UX for motion-sensitive users (likely).

## High-level view

The oasis panel height fix is straightforward: world-class.css drops `height: 500px` to `height: auto`, and visual-final-polish.css adds the same with a `min-height: 320px` floor and existing `max-height: 520px` ceiling. Both files now declare `height: auto` redundantly since world-class.css loads last and wins the cascade.

The teal glow removal in global-icon.css replaces a three-layer box-shadow (border + glow + depth) with a single soft depth shadow. The shadow is a bare `rgba(0,0,0,0.18)` literal, the one remaining raw color value introduced by this diff despite the token-cleanup goal.

The bottom-nav scroll-hide adds a data-attribute-driven CSS transition and JS scroll-direction detection in AppShell, piggybacking on the existing rAF-throttled scroll handler. The hidden state is not reset on route changes, so navigating away from a long-scrolled page can leave the nav hidden on the next page until the user scrolls up.

The widget positioning drops from `bottom: 80px` to `bottom: var(--sp-5)` (20px). The original 80px cleared the bottom nav; 20px may cause overlap on mobile viewports where the nav is visible.

## Bottom-nav scroll-hide lifecycle gap

The scroll-direction tracking uses a `lastScrollTopRef` with a 10px dead-zone threshold to avoid flicker on elastic scroll. The route-change effect resets `scrolled` and scrolls content to top but never resets `bottomNavHidden`:

```tsx
useEffect(() => {
  contentRef.current?.scrollTo({ top: 0, behavior: 'instant' as ScrollBehavior });
  setScrolled(false);
  // missing: setBottomNavHidden(false);
  // missing: lastScrollTopRef.current = 0;
}, [location.pathname]);
```

When a user scrolls down on page A (hiding the nav), then taps a link, they arrive at page B with scroll reset to 0 but the nav still hidden. The `scrollTo(0)` fires the scroll handler which compares `currentTop = 0` against the stale `lastScrollTopRef.current`. Since 0 < old - 10, the handler *may* show the nav again on the next frame. But `scrollTo` with `behavior: 'instant'` may or may not fire the scroll event synchronously depending on the browser (Chrome does; Safari sometimes doesn't). The safe fix is to explicitly reset both `bottomNavHidden` and `lastScrollTopRef.current` in the route-change effect. **Confidence: confirmed** for the missing reset; **likely** for the Safari race.

## Reduced-motion and the scroll-hide transform

The `@media (prefers-reduced-motion: reduce)` block disables the transition but still applies `transform: translateY(100%)` when `data-hidden="true"`:

```css
@media (prefers-reduced-motion: reduce) {
  .bottom-nav { transition: none !important; }
  .bottom-nav[data-hidden="true"] { transform: translateY(100%); }
}
```

For users who prefer reduced motion, the nav teleports off-screen instantly. The typical accessibility expectation is that elements remain stable or state changes happen without spatial displacement. A nav that vanishes without animation is harder to track than one that smoothly exits. Consider removing the transform rule entirely inside the reduced-motion block so the nav stays visible regardless of scroll direction. **Confidence: likely.**

## Widget positioning after `bottom: var(--sp-5)`

The change from `bottom: 80px` to `bottom: var(--sp-5)` (20px per tokens.css) moves the widget 60px closer to the screen edge. The original 80px was presumably chosen to clear the bottom nav (~60px tall). Since world-class.css loads *after* visual-final-polish.css (per the import order in main.tsx), this 20px value wins the cascade. If visual-final-polish.css Section 9 had a media query raising the widget on mobile, it would be overridden. Verify on a mobile viewport that the oasis trigger doesn't sit behind the nav. **Confidence: possible** (depends on whether a separate media query elsewhere re-positions the widget above the nav on small screens).
