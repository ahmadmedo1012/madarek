# Visual layer rewrite: scholarly restraint over decorative excess

The entire CSS visual layer was rebuilt from scratch — tokens, app shell, landing, dashboard, auth, lecture, and matrix styles — to shift from a "flashy glassmorphism" aesthetic to a restrained, scholarly tone. Decorative pseudo-elements (gradient hairlines, floating orbs, dot-grid textures, animated shimmer bars, cinematic hero gradients) were systematically removed. The token system was retuned with softer shadows, smaller radii, faster motion, and a warm-neutral palette. The LandingPage.tsx was lightly touched to replace inline KPI styles with `data-tone` attributes and remove `ai-glow` class references.

**Watch for:** Duplicate landing definitions between app.css and landing.css create specificity conflicts and maintenance burden (confirmed). Hardcoded light-mode colors in KPI `data-tone` selectors will produce poor contrast on dark backgrounds (confirmed). The `landing-bento-icon[data-tone="tertiary"]` variant is referenced in JSX but has no CSS (confirmed).

## High-level view

The token system moves from saturated brand blues and cyans to desaturated scholarly tones. Radii shrink uniformly (18→12 for `--r-lg`, 28→20 for `--r-2xl`), shadows lose their inner-glow layers, and motion durations drop by ~15%. The "Stitch" aliased tokens (`--st-r-*`, `--st-container-max`, etc.) are gone entirely — no remaining references exist.

Components lose their decorative pseudo-elements uniformly. Metric cards switch from a `::before` top-bar to a colored `border-inline-start`, which is a sound RTL-safe pattern. The landing page duplicates its selectors across `app.css` (section 25) and `landing.css` with divergent values (e.g. `min-height: 480px` vs `420px`), so final rendering depends on stylesheet load order.

The dashboard strips all animated decorations and removes nearly all `!important` declarations. The auth page flattens its gradient-heavy left panel and replaces heavy focus rings with a subtle 2px accent ring — but `landing-auth-v3.css` re-declares structural auth selectors that also live in app.css, creating another load-order dependency.

## Duplicate landing styles across two files

Landing-page selectors live in two independent files: `app.css` (around line 2080–2370) and `landing.css` (the entire file). Both define `.landing-hero`, `.landing-hero-showcase`, `.landing-hero-float-card`, `.landing-cta-glass .btn`, `.landing-bento-card`, `.landing-bento-icon`, and `.kpi-strip`. The values diverge:

| Selector | app.css | landing.css |
|----------|---------|-------------|
| `.landing-hero-showcase` min-height | 480px | 420px |
| `.landing-bento-card:hover` transform | translateY(-3px) | translateY(-2px) |
| `.landing-hero-float-card` nth-child animation names | `landing-float` / `landing-float-reverse` | `float` / `float-reverse` |
| `.landing-hero` grid columns | 1.1fr 1fr | 1fr 1fr |

Whichever file loads last in the cascade wins. The app.css version uses `!important` on `.landing-hero-float-card` to force its values through — a symptom of fighting the duplication rather than resolving it. Additionally, the app.css landing section has no 900px responsive breakpoint, so its duplicated hero/bento selectors won't gracefully stack at tablet widths.

## Missing data-tone="tertiary" styling for bento icon

LandingPage.tsx line 207 applies `data-tone="tertiary"` to a `.landing-bento-icon`:

```tsx
<div className="landing-bento-icon" data-tone="tertiary">
```

Neither landing.css nor app.css define a selector for this attribute. The icon renders with the base accent-blue color rather than the intended teal/tertiary. Add:

```css
.landing-bento-icon[data-tone="tertiary"] {
  background: color-mix(in srgb, var(--md-tertiary-container) 15%, transparent);
  color: var(--md-on-tertiary-container);
}
```

## KPI icon colors ignore dark mode

The `data-tone` selectors in landing.css (lines 425–442) use hardcoded hex values designed for light backgrounds:

```css
[data-tone="blue"] .kpi-icon {
  background: rgba(41, 82, 200, 0.10);
  color: #1e40af;     /* dark navy ink */
}
```

On the dark theme's `--bg: #0f1117`, `#1e40af` has a contrast ratio of about 2.2:1 — functionally invisible for small icons. These selectors need `[data-theme='dark']` overrides or should use semantic tokens (`--accent`, `--success`, etc.) that already adapt per theme. The old code used the same hardcoded values as inline styles, so this is a pre-existing issue being locked in by the new CSS structure rather than a regression.

## Sidebar active-item visual weight

The active nav-item in the sidebar changed from a gold background with dark text and a gold glow (`box-shadow: 0 2px 12px ...`) to a semi-transparent white overlay (`rgba(255,255,255,0.14)`) with white text. The new treatment is significantly more subtle — verify it provides enough visual weight for users to orient themselves, especially at a glance in peripheral vision.

## Auth-page stylesheet overlap

`landing-auth-v3.css` now defines `.auth-split`, `.auth-left`, `.auth-glass-card`, `.auth-right`, `.auth-back-home`, and `.auth-overlay-madarek` — all of which also exist in app.css section 26. The auth-v3 file re-declares structural properties (grid-template-columns, padding, border-radius) without `!important`, so whichever loads last applies. If load order changes, the auth layout will break silently.
