# Design system overhaul: token palette, landing page tokenization, CSS consolidation

A sweeping redesign of the Madarek design foundation. The old "Google Stitch" palette (navy #003461, gold #FED65B, dark teal #003A3B) is replaced with a new identity: primary blues (#5B8DEF–#3B6CC7), teal #4ECDC4, and muted gold #C8962E. The token system gains a proper neutral scale, consolidated spacing/radius/shadow tokens, and an Arabic-first font stack. On the landing page, all hardcoded inline color styles are replaced with `data-tone` attributes driven by CSS, and landing-pro.css is stripped from a conflicting override sheet (with `!important` everywhere) down to a minimal premium-additions layer. Breakpoints are standardized to 1024/640/480px.

**Watch for:** The `landing-pro.css` button override now re-specifies the same `.landing-header-login .btn` selector that `landing.css` already defines — last-loaded wins, but loading order is implicit and fragile (likely). The `data-tone` system duplicates its selector block for `.kpi-icon` and `.landing-feature-icon` with identical values, begging for a shared `[data-tone]` rule (confirmed). One remaining `!important` in `landing.css` (`.kpi-cell` border removal at 480px) survived the cleanup (confirmed).

## High-level view

The token palette is rebuilt from first principles with new color scales. The old MD3 tokens are preserved as backward-compat aliases pointing into the new scales, which means existing app components that reference `--md-primary` continue to resolve — but to a different hue (#3B6CC7 vs the old #003461). The cinematic theme is removed entirely; only dark and light remain.

The landing page component removes all inline `style={{}}` for colors, replacing them with a `data-tone` attribute pattern. The CSS in `landing.css` maps each tone to semantic token pairs, so icons respect theme changes automatically. The ministry strip becomes a simple `var(--surface-2)` bar.

The CSS architecture cleanup consolidates duplicate selectors across `landing.css` and `landing-pro.css`. The old `landing-pro.css` defined its own `.landing-header`, `.landing-hero::before`, `.landing-hero-img`, and title font overrides with `!important` — all removed. What remains is purely additive: gold accent variables, eyebrow pill, button gold treatment, card hover unification.

The `landing-auth-v3.css` CTA buttons drop all `!important` declarations and the gradient references new token variables. The responsive breakpoint is aligned from 900px to 1024px.

## Token palette rebuild and MD3 alias drift

The old MD3 aliases (`--md-primary`, `--md-secondary`, etc.) are remapped to point at the new scale. The resolved *color* changes from dark navy `#003461` to blue `#3B6CC7`:

```css
/* Before */
--md-primary: #003461;
/* After */
--md-primary: var(--color-primary-600);  /* resolves to #3B6CC7 */
```

Every component in the app that references these aliases — sidebar headers, buttons, links, chart accents — will shift hue. The diff only touches landing-related CSS, so this palette shift propagates silently to the rest of the app without corresponding visual validation in those components (likely regression risk).

## Data-tone pattern: duplicated selectors

The `data-tone` attribute mapping is defined twice with identical values:

```css
.kpi-icon[data-tone="primary"] {
  background: var(--accent-soft);
  color: var(--accent);
}
.landing-feature-icon[data-tone="primary"] {
  background: var(--accent-soft);
  color: var(--accent);
}
/* Same duplication for success, tertiary, secondary */
```

This should be a single rule: `[data-tone="primary"]` (unqualified) or `.landing [data-tone="primary"]` (scoped). As more components adopt data-tone, maintaining N copies will drift.

## landing-pro.css specificity depends on load order

`landing.css` defines `.landing-header-login .btn` with `background: var(--accent)`. `landing-pro.css` redefines the same selector with `background: var(--lp-gold)`. No specificity difference, no `!important` — the gold treatment wins purely because `landing-pro.css` loads after `landing.css`.

The file declares `@layer tokens, base, components, pages, overrides` in `tokens.css`, but neither landing file opts into any layer. Everything lives in the implicit outer layer, so load order is the only tiebreaker. If a bundler reorders imports (Vite's CSS module handling, code-splitting, or a future refactor), the gold accent silently disappears. Adding `@layer pages` to `landing.css` and `@layer overrides` to `landing-pro.css` would make the cascade explicit.

## CTA token migration: inconsistent fallback strategy

In `landing-auth-v3.css`, the CTA gradient uses bare token references:

```css
linear-gradient(160deg, var(--color-primary-900) 0%, var(--color-primary-600) 50%, var(--color-primary-400) 100%);
```

But adjacent properties in the same file use the fallback pattern:

```css
color: var(--color-neutral-50, #ffffff);
background: var(--color-gold-400, #fbbf24);
```

If `tokens.css` fails to load, the gradient renders as `transparent` — a blank CTA section — while text at least falls back to white. Either all token references should include fallbacks consistently, or none should.

## Removed cinematic theme: potential persisted-preference breakage

The `[data-theme='cinematic']` block is removed. If any user had `data-theme="cinematic"` persisted in localStorage via Zustand, the app falls through to `:root` dark defaults — accent shifts from amber `#ffbf00` to blue. The theme store should be updated to exclude 'cinematic' and migrate persisted values (possible — depends on whether cinematic was ever exposed in the UI's theme picker).
