# 12 — النشر والتشغيل (Render + Neon)

النشر **تلقائي** عند كل دفع إلى `main` (`autoDeploy: true`) — لا يوجد
إجراء نشر يدوي في المستودع. المخطط: `render.yaml`. لا توجد خطوات نشر في
CI (يبني ويفحص فقط).

> **قرار الاستضافة (المرحلة 10 — r182):** البقاء على Render المتكامل
> قرار موثّق بمقارنة رسمية مؤرّخة للبدائل (Vercel بوضعيْه) في
> [`docs/architecture/hosting-decision.md`](architecture/hosting-decision.md)
> — حدّ 4.5MB لجسم وظائف Vercel يكسر رفع PDF الحالي، وخطة Hobby
> غير تجارية حصرًا. لا تُفتح ملفات Vercel في هذا المستودع دون إعادة
> فتح القرار الموثّق.

## المتطلبات

1. حساب Render (خدمة Blueprint) + قاعدة Neon PostgreSQL.
2. سرّا JWT مختلفان (يولدهما Render تلقائيًا إن أنشأت الخدمة من المخطط).
3. سلسلة اتصال Neon **pooler**.

## الخطوات الثلاث (كما في README)

1. اربط المستودع بـRender: **New + → Blueprint** واختر `madarek`.
   `render.yaml` ينشئ خدمة `web` باسم `madarek` (runtime node، خطة
   مجانية، إقليم `virginia` — بجوار أساسي Neon لتقليل زمن الاستعلام).
2. من تبويب **Environment**، ضع `DATABASE_URL` بسلسلة Neon pooler:
   `postgresql://…?sslmode=require&channel_binding=require`.
3. دفع إلى `main` → يبني وينشر تلقائيًا.

## ماذا يفعل البناء فعليًا؟

```text
buildCommand: npm ci --include=dev && npm run build
```

- `--include=dev` إلزامي: Render يضبط `NODE_ENV=production` قبل التثبيت،
  وبلا هذه العلامة ستتخطى أدوات البناء (tsc/vite/prisma CLI).
- `npm run build` (الجذر) = بناء الواجهة → بناء الخلفية → `db:deploy`
  الذي يشغّل **`prisma migrate deploy`** عبر `backend/scripts/migrate-deploy.mjs`
  (اختيار pooler/direct ذكي + إيقاظ Neon + 3 محاولات — التفصيل في
  [07-database](07-database.md)) → ثم **`db:seed`** (r183): بذرة مؤسستَي
  العرض تعمل داخل بيئة البناء **كإقلاع أولي تلقائي فقط** — قاعدة
  فارغة (لا مستخدمين) تُهيَّأ ذاتيًا بالكامل؛ أما **القاعدة المؤسَّسة
  فتُتخطى البذرة بالكامل** (صفر كتابات: لا تصفير كلمات مرور ولا مساس
  بإعدادات أو سجلات — النشر العادي لا يعيد ضبط بيانات اعتماد أبدًا).
  إعادة ضبط حسابات العرض الواعية (كلمات مرور العرض → `Madarek2026!`
  وتحديث نضارة العرض) فعل مشغِّل صريح ومعزول:
  `MADAREK_SEED_FORCE=1 npm run db:seed:force` — وحتى في مسار FORCE
  يبقى العقد: التقدم التعليمي المُدار من المستخدمين (درجات/إتقان/
  مشاهدات/مستويات مهارات) **لا يُرجَع أبدًا** (upserts إنشاء-فقط) —
  انظر رأس `backend/prisma/seed.ts` وعقد الاختبار في
  `backend/tests/integration/seed-idempotency.test.ts`.
- ثم `startCommand: npm run start` → `node backend/dist/index.js`.

> سبب «بلا DB» لبناء CI: الخطوة الأخيرة أعلاه تتطلب قاعدة حية، لذا يبني
> CI كل workspace منفصلًا ولا يلمس الترحيلات (`.github/workflows/ci.yml`).

## المتغيرات في `render.yaml`

| المتغير | القيمة/السلوك |
|---|---|
| `NODE_ENV` | `production` (يفعّل خدمة SPA من Express وكوكي Secure) |
| `NODE_VERSION` | `'22'` مثبتة (r164-l) — **مطابقة حرفيًا لإصدار CI** داخل نطاق `engines` ‏`>=20 <25` (الإصدار LTS المدعوم — Node 20 انتهى في أبريل 2026)؛ بلا تثبيتها يختار Render إصداره الافتراضي وقد ينحرف عن الإصدار الذي اختُبر عليه القفل |
| `TZ` | `UTC` مثبت — لا تغيّره (حواف أيام الحضور، انظر [03](03-architecture.md)) |
| `DATABASE_URL` | `sync:false` — تضبطه يدويًا |
| `JWT_ACCESS_SECRET` / `JWT_REFRESH_SECRET` | `generateValue: true` (32 محرفًا = الحد الأدنى في `env.ts` بالضبط؛ لا ترفع الحد دون خطة) |
| `CORS_ORIGINS`, `INTERNAL_SERVICE_TOKEN`, `DIRECT_DATABASE_URL` | `sync:false` اختيارية — سلوكها في [06-configuration](06-configuration.md) |
| `STORAGE_DRIVER`, `STORAGE_DIR`, `S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` | `sync:false` اختيارية — متغيرات تخزين رفعات PDF: بلا ضبط = سائق محلي (زائل على Render، مع تحذير إقلاع واحد)؛ لدوام الملفات اضبط `STORAGE_DRIVER=s3` + الأربعة `S3_*` (الخطوات أدناه) — التفصيل في [06-configuration](06-configuration.md) |
| `AI_PROVIDER`, `AI_BASE_URL`, `AI_API_KEY`, `AI_MODEL` | `sync:false` اختيارية — متغيرات مزوّد المساعد الذكيّ: بلا ضبط = محرّك محلي (بلا استدعاءات خارجية)؛ لنموذج حقيقي اضبط `AI_PROVIDER=openai` + `AI_API_KEY` + `AI_MODEL` (الخطوات أدناه) — التفصيل في [06-configuration](06-configuration.md) |

## فحص الصحة والتحقق بعد النشر

- `healthCheckPath: /api/v1/health` — يفحص `SELECT 1` بمهلة 5 ثوانٍ
  (امتصاص بدء Neon البارد) ويرد `{ ok, dbLatencyMs, env, buildId }`.
- بعد كل نشر: شغّل `npm run smoke` (فحص الدخان بعد النشر — القسم
  التالي) فيطبع جدول فحوص واضحًا، ثم تحقق يدويًا من دخول حساب
  تجريبي وصفحة لوحة — `BUILD_ID` ثابت نصي يساعد على التمييز.
- سجلات التشغيل: تبويب **Logs** في Render (pino JSON بمستوى info في
  الإنتاج مع حجب أسرار).

## فحص الدخان بعد النشر — `npm run smoke`

سكربت `scripts/smoke-deploy.mjs` (r164-l) — Node خالص **بلا أي
اعتماديات** (يعمل على أي تثبيت node حتى بلا `node_modules`)، يفحص
**نشرًا حيًا** ويعرض جدول PASS/FAIL ويخرج برمز 0/1 — يصلح للتشغيل
اليدوي بعد كل نشر أو لربطه بأتمتة المالك:

```bash
npm run smoke                                 # الافتراضي: madarek.onrender.com
BASE_URL=https://<نطاقك> npm run smoke        # هدف مختلف عبر البيئة
npm run smoke -- https://<نطاقك>              # أو وسيطًا موضعيًا
SMOKE_EMAIL=<بريد> SMOKE_PASSWORD=<كلمة> npm run smoke   # + حلقة دخول كاملة
# r180: فحص عزل المؤسستين — زوّد زوجًا ثانيًا لمستخدم مؤسسة أخرى:
SMOKE_EMAIL=<بريد أ> SMOKE_PASSWORD=<كلمة أ> \
SMOKE_EMAIL2=<بريد ب> SMOKE_PASSWORD2=<كلمة ب> npm run smoke
```

الفحوص الخمسة:

1. **الصحة**: `GET /api/v1/health` → ‏200 JSON فيه `ok=true` +
   `dbLatencyMs` (يُبلّغ عن قيمته) + `env` — بمهلة 90 ثانية وإعادة
   محاولة واحدة (امتصاص إسبات الخطة المجانية وبداية Neon الباردة).
2. **الرئيسية**: `GET /` → ‏200 HTML فيه جذر تثبيت التطبيق
   (`id="root"`) **وترويسة CSP تحمل بصمات `sha256-`** (قرار D7 —
   غيابها يعني خللًا في ترويسات الأمان لا مجرد تحذير).
3. **صفحة الدخول**: `GET /auth` → ‏200 (مسار SPA fallback يخدم
   `index.html`).
4. **حلقة الدخول (اختيارية)**: تعمل فقط عند توفير `SMOKE_EMAIL` +
   `SMOKE_PASSWORD` **معًا** (المعرّف: البريد أو رقم القيد — كلاهما
   مقبول في مسار الدخول): `POST /api/v1/auth/login` → توكن وصول →
   `GET /api/v1/auth/me` بترويسة `Bearer` → مطابقة الدور بين
   الاستجابتين. لا تُطبع كلمة المرور ولا التوكن أبدًا، والبريد يظهر
   مقنّعًا (`a***@…`). تقديم متغير واحد فقط دون الآخر = فحص FAIL
5. **عزل المؤسستين (r180، اختياري)**: يعمل فقط عند توفير
   `SMOKE_EMAIL`/`SMOKE_PASSWORD` **و** `SMOKE_EMAIL2`/
   `SMOKE_PASSWORD2` (مستخدم من مؤسسة أخرى): يسجّل الدخول
   بالمستخدمين، يجلب تسجيلات كل منهما (`GET /enrollments/me`)،
   يتحقق أن مجموعتي الشعب **منفصلتان تمامًا**، ثم يطلب المستخدم
   الأول شعبة مؤسسة الثاني (`GET /offerings/:id/full`) ويتحقق أن
   الرفض 403/404 — أبدًا 200. (مثال جاهز: الطالبان التجريبيان
   `student@zu.edu.ly` و`student2@demo.madarek.ly`.)
   برسالة صريحة (لا تخطٍّ صامت).

> قاعدة صدق: الفحص يلمس النشر الحي فقط ولا يُشغّل داخل CI أبدًا
> (وثيقة 11). إن ظهر فحص أحمر: راقب تبويب **Logs** في Render ثم أعد
> المحاولة — حد المعدل على تسجيل الدخول (429) فحصٌ FAIL صادق
> يزول بعد دقيقة.

## التراجع عن إصدار معطوب

1. **الأسرع**: Render → تبويب **Events/Manual Deploy → Rollback** إلى
   النشر السابق السليم (لا يلمس قاعدة البيانات).
2. إن كان السبب ترحيلًا: الترحيلات **إضافية بالتصميم**؛ التراجع الكودي
   مع ترحيل رجوعي جديد مكتوب يدويًا فقط إن كان لا مفرّ — بقرار واعٍ
   ومُختبر على بيئة تطوير أولًا.
3. صحّح الكود ودفع — autoDeploy سيغيرن النشر الجديد.

> التراجع أعلاه يعالج **الكود**. للتراجع في **البيانات** (استعادة قاعدة
> أو لحظة زمنية) انظر قسم «النسخ الاحتياطي والاستعادة» أدناه.

## النسخ الاحتياطي والاستعادة (دليل المالك — r164-l، السكربتات r166c)

> **إفصاح صدق:** هذا الدليل كُتب ورُوجع من داخل المستودع، وسكربتا
> المشغِّل أدناه (`db:backup`/`db:restore`) مبنيان ومختبَران
> (حراسهما ووضعهما التجريبي مثبّتان باختبارات وحدة بلا DB) — لكن
> **تجربة النسخ/الاستعادة الفعلية نُفِّذت في r183 (2026-10-17)** من
> قاعدة الإنتاج الحيّة إلى قاعدة عزل معزولة بتحقق شامل وإقلاع تطبيق
> production ودخان 5/5 — التنفيذ الفعلي بقي **فعل مالك** لتكراره
> الدوري؛ السكربتات تجعله
> قابل التنفيذ بأمان (تحقّق من الأدوات، تقنيع السلاسل في كل المخرجات،
> ورفض الاستعادة فوق قاعدة الإنتاج افتراضيًا) — وسجّل نتيجتك في
> [docs/runbooks/restore-exercise-log.md](runbooks/restore-exercise-log.md).

### 1) ما تديره Neon تلقائيًا

- كل مشروع Neon يملك نسخًا احتياطية ذاتية حسب خطة المشروع، ومنها
  **الاستعادة النقطية الزمنية** (Point-in-Time Restore): من لوحة
  المشروع اختر لحظة زمنية واستعد إلى **فرع جديد** — الإنتاج نفسه لا
  يُلمس، وتحصل على قاعدة تحمل حالة تلك اللحظة.
- نافذة الاحتفاظ ومدى توفر PITR يختلفان **باختلاف خطة Neon** — تحقق
  من لوحة مشروعك (Project → Settings/Backups) ولا تفترض رقمًا من هنا.
- مسار العمل المقترح عند حادثة بيانات: استعِد إلى فرع جديد → تحقق
  منه (القائمة أدناه) → إن سليم وجّه `DATABASE_URL` في Render إليه
  مؤقتًا (Environment → Save = إعادة نشر) — ثم صحّح الأصل بقرار واعٍ.

### 2) نسخة يدوية بقواعد «استراتيجية الرابطين»

الإنتاج يخدم الطلبات عبر **pooler** (`DATABASE_URL`)، وأعمال الصيانة
(الترحيلات والنسخ/الاستعادة) تحتاج الاتصال **المباشر** — هذا حرفيًا
ترتيب المرشحات في `backend/scripts/migrate-deploy.mjs`:

1. `DIRECT_DATABASE_URL` إن ضبطته في Render (المفضلة).
2. وإلا اشتقّ المباشر بنفسك من سلسلة الـpooler: **احذف `-pooler` من
   اسم المضيف** واحذف معاملات `pgbouncer`/`connection_limit` (افتح
   سلسلة الاتصال من لوحة Neon → Connection Details → الاتصال المباشر
   نسخة جاهزة من ذلك).

> **r183 — طابق إصدار عميل pg مع الخادم:** استعادة بعميل 17.11 على
> خادم Neon 16.15 تفشل بخطأ `unrecognized configuration parameter
> "transaction_timeout"` (خاصية 17 لا يعرفها 16) — اِستخدم عميلًا
> بنفس الإصدار الأكبر للخادم (16.15↔16.15 هنا). الدرس كامل في مدخل 3
> من سجل التجارب.

قالب النسخ (r166c: سكربت المشغّيل فوق القالب الخام — على جهاز فيه
أدوات PostgreSQL):

```bash
# المتغيران من Render → Environment (قيم سرية — لا تضعها في ملف)
PG_DIRECT='<سلسلة الاتصال المباشر — بلا -pooler>'

# الطريقة الموصى بها: سكربت db:backup (scripts/db-backup.mjs) —
# يتحقق أن pg_dump مثبت (وإلا رسالة تثبيت ثنائية اللغة)، يقرأ
# المصدر من متغير البيئة بالاسم فقط، يقنّع السلسلة في كل المخرجات،
# ويطبع الحجم وبصمة sha256 للملف بعد النسخ:
npm run db:backup -- --url-env PG_DIRECT --label pre-migration
npm run db:backup -- --url-env PG_DIRECT --dry-run   # معاينة الأمر بلا تنفيذ

# الأمر الخام الذي يشغّله السكربت (قانون هذا الدليل نفسه —
# نسخة كاملة بصيغة custom قابلة للضغط والاستعادة الانتقائية):
pg_dump --format=custom --no-owner --no-privileges \
  --file="madarek-$(date -u +%Y%m%dT%H%M%SZ).dump" "$PG_DIRECT"
```

قالب الاستعادة إلى قاعدة/فرع **تجريبي** (لا إلى الإنتاج مباشرة أبدًا —
الفرع الجديد في Neon يبدأ فارغًا فلا تحتاج `--clean`) — عبر سكربت
`db:restore` (scripts/db-restore.mjs) الذي يضيف حراسة صريحة:

- **هدف صريح إلزامي**: `--url-env <NAME>` — السكربت لا يقرأ
  `DATABASE_URL` ضمنيًا للهدف أبدًا (الاستعادة قرار واعٍ).
- **حارس الرفض الصارم**: إن طابق الهدفُ قاعدة الإنتاج
  (`DATABASE_URL`) رفض السكربت التنفيذ ما لم تُمرّر
  `--confirm-live-restore` بوعي — رسالة الرفض ثنائية اللغة
  وتشرح المسار الآمن (فرع جديد ← تحقق ← قرار).
- `--dry-run` يطبع الأمر الدقيق بالسلسلة المقنّعة والحارس يعمل حتى
  في المعاينة.

```bash
STAGE_DIRECT='<سلسلة الاتصال المباشر لفرع التجربة من لوحة Neon>'

npm run db:restore -- --url-env STAGE_DIRECT --file madarek-YYYYMMDDTHHMMSSZ.dump
npm run db:restore -- --url-env STAGE_DIRECT --file <dump> --dry-run

# الأمر الخام الذي يشغّله السكربت:
pg_restore --no-owner --no-privileges \
  --dbname="$STAGE_DIRECT" madarek-YYYYMMDDTHHMMSSZ.dump
```

- `--no-owner --no-privileges`: أسماء الأدوار في Neon مُدارة ولا تُنقل
  مع الملف؛ Prisma لا يحتاجها (الاتصال الوحيد من الخلفية — وثيقة 07).
- الملف الناتج (`.dump`) يحمل معه جدول `_prisma_migrations` — أي حالة
  المخطط مطبوعة في النسخة نفسها (التحقق رقم 4 أدناه).

### 3) تجربة الاستعادة على بيئة تجريبية (قائمة المالك)

> الهدف: إثبات أن النسخة **قابلة للاستعادة فعلًا** قبل الحاجة إليها.
> **r167:** نُفِّذت تجربة محلية كاملة (نسخ → حارس → استعادة → تحقق →
> ربط تطبيق حيّ → تدريب تدوير كلمة المرور) على PostgreSQL محليّ ببيانات
> البذرة — مدخل 1 في
> [docs/runbooks/restore-exercise-log.md](runbooks/restore-exercise-log.md)
> يحمل القيم المقيسة.
> **r183 (2026-10-17): تجربة الإنتاج الفعلية مكتملة** — من قاعدة
> الإنتاج الحيّة إلى قاعدة عزل في نفس مشروع Neon، بتحقق شامل (80
> جدولًا واحد-لواحد، 124 قيد مفاتيح بلا يتامى) + إقلاع تطبيق
> production + دخان 5/5 شاملًا عزل المؤسستين — المدخل 3 في السجل
> يحمل كل القيم المقيسة والدروس (مطابقة إصدار العميل للخادم، التحقق
> عبر الاتصال المباشر لا الـpooler، وDROP DATABASE WITH (FORCE)).

```text
□ 1. خذ نسخة يدوية بالقالب أعلاه واحفظ الملف خارج جهاز الخدمة
     (تخزين كائنات/قرص خارجي) — النسخة على نفس القاعدة ليست نسخة.
□ 2. أنشئ فرعًا جديدًا في Neon باسم restore-exercise-<تاريخ>.
     متوقع: فرع فارغ بسلسلتي اتصال خاصتين به (pooler + مباشر).
□ 3. استعِد الملف إلى الفرع بالقالب أعلاه.
     متوقع: pg_restore ينتهي بلا أخطاء (التحذيرات المرتبطة بالأدوار
     طبيعية مع --no-owner).
□ 4. تحقق من سلامة الاستعادة بالاستعلامات:
     (r167) البديل المؤتمت: `STAGE_DIRECT="<url>" npm run db:verify
     -- --url-env STAGE_DIRECT` يشغّل الفحوص التالية كاستعلامات حقيقية
     ويطبع حكمًا مقيسًا PASS/WARN/FAIL — أو نفّذها يدويًا:
     psql "$STAGE_DIRECT" -c '\dt'
       متوقع: قائمة جداول المخطط كاملة (~76 جدولًا).
     psql "$STAGE_DIRECT" -c "SELECT migration_name, finished_at
       FROM _prisma_migrations ORDER BY finished_at DESC LIMIT 3;"
       متوقع: آخر ترحيل مطابق لما على الإنتاج
       (20261013150858_checkpoint_answer_memory وقت كتابة هذا الدليل).
     psql "$STAGE_DIRECT" -c 'SELECT role, count(*) FROM "User"
       GROUP BY role ORDER BY count(*) DESC;'
       متوقع: توزيع أدوار مطابق للإنتاج تقريبًا (أرقامك أنت).

       متوقع: عدد قريب من عدّاد لوحة المالك (إحصاءات التسجيلات).
□ 5. اربط التطبيق بالفرع تحققًا حيًا: خذ سلسلة pooler الفرع وضبطها
     في backend/.env محليًا ثم شغّل الخلفية محليًا وافتح
     /api/v1/health ثم صفحة دخول — أو استخدم فحص الدخان مع هدف
     منفصل إن نشرت الفرع كـpreview.
□ 6. تحقق أن الإنتاج لم يُمس (تحقق التراجع):
     - من Render → Environment: `DATABASE_URL` ما زال يشير لقاعدة
       الإنتاج (لم يتغير أثناء التجربة كلها).
     - نفّذ `npm run smoke` — متوقع: كل الفحوص PASS كما قبل التجربة.
□ 7. نظّف: احذف فرع التجربة من لوحة Neon (Branches → Delete) حتى
     لا تتراكم فروع قراءة على حدود الخطة، واحتفظ بالملف في تخزينك.
```

### 4) تدوير كلمات المرور من طرف المشغّل — ومسار استعادة حساب المالك (r166c)

سكربت `npm run db:rotate-password`
(`backend/scripts/rotate-demo-passwords.mjs`) هو **المسار المفوّض**
لتدوير كلمة مرور أي حساب بيد من يملك `DATABASE_URL` (السرّ نفسه هو
التفويض) — وهو **مسار استعادة حساب المالك عند فقدان كلمته**: لا يوجد
مسار إدارة داخل التطبيق لإعادة تعيين كلمة المالك.

```bash
# 1) صدّر كلمة قوية باسم متغير — لا تُمرّر وسيطًا أبدًا ولا تُطبع:
export NEW_PASSWORD="$(openssl rand -base64 24)"

# 2) معاينة (قراءة فقط: يتحقق من الحساب ويعرض التغيير المخطط):
npm run db:rotate-password -- --email owner@zu.edu.ly --new-password-env NEW_PASSWORD --dry-run

# 3) التنفيذ — يتطلب --yes (وإلزامي كذلك عند NODE_ENV=production):
npm run db:rotate-password -- --email owner@zu.edu.ly --new-password-env NEW_PASSWORD --yes
```

دلالات السكربت تطابق `changePassword` في التطبيق
(`auth.service.ts`): تجزئة argon2id **بنفس معاملات
`src/lib/password.ts`** (اختبار وحدة يثبّت التطابق حرفيًا فلا يتباعد
المصدران)، وتحديث **ذرّي واحد** يرفع `tokenVersion` (إبطال كل
الجلسات على كل الأجهزة) ويصفّر عدّاد محاولات الدخول الفاشلة ويفتح
القفل، مع رفض الحساب المجهول وغير النشط، ورفض تنفيذ الإنتاج بلا
`--yes`. حدّ الطول المفروض 8–72 محرفًا (سياسة `passwordSchema`
نفسها)؛ قائمة كلمات المرور الشائعة حرس طبقة الـDTO داخل التطبيق —
اختر كلمة قوية كما في الأمر أعلاه.

> حسابات العرض الأربعة (student/teacher/admin/quality@zu.edu.ly)
> دُوّيرت في الإنتاج عبر التطبيق نفسه (`/auth/change-password`) —
> كلمة `1234` لم تعد مقبولة هناك. هذا السكربت للأغراض المشغّلية
> المستقبلية ولحساب المالك خاصة.

### 4ب) تجهيز حساب مالك باسم المشغّل — provision-owner (r187)

`npm run db:provision-owner` (`backend/scripts/provision-owner.mjs`)
هو المسار المفوَّض لإنشاء **حساب مالك عالمي واحد بهوية المشغّل**
(بريده المتحقّق) — ويكمل تدوير الكلمات أعلاه: التدوير يدير حسابًا
قائمًا، وهذا ينشئ الهوية الجديدة. العقد:

- **لا مسار عام يمنح OWNER أبدًا** — السكربت يعمل بيد من يملك
  `DATABASE_URL` فقط (نفس فلسفة التدوير: السرّ هو التفويض)،
  ورفض `--yes` في الإproduction إلزامي.
- **يرفض ترقية هوية قائمة بصمت**: بريد موجود بدور آخر → رفض قاطع
  (لا تصعيد امتيازات)؛ بريد مالك قائم → يوجّهك لمسار التدوير.
- **سرّ لمرة واحدة**: إن لم تمرّر `--password-env` يولّد السكربت
  سرًّا عشوائيًا (24 بايت) ويطبعه **مرة واحدة** بين علامات واضحة؛
  كلمة المرور المختارة عبر متغير البيئة لا تُطبع أبدًا.
- **صف تدقيق**: كل إنشاء يسجّل `OWNER_PROVISION`
  (مصدر operator-script) في `AuditLog` داخل نفس المعاملة.
- **`--suspend-demo-owner`**: يعلّق حساب العرض `owner@zu.edu.ly`
  (isActive=false + إبطال جلساته) **بعد** إنشاء الحساب الجديد
  وبنفس المعاملة — لا تنتهي المنصة بصفر مالكين نشطين أبدًا.
- **مثبَّت باختبارات**: عقد السكربت كله (معاملات argon، حدود
  السياسة، الرفض، الطباعة الوحيدة للسرّ) مسمر في
  `backend/tests/modules/db-ops.test.ts` (r187).

```bash
cd backend
DATABASE_URL="<إproduction>" node scripts/provision-owner.mjs \
  --email <بريدك> --yes --suspend-demo-owner
```

> **حالة r187 الفعلية:** كلمة مرور حساب المالك التجريبي على
> الإنتاج **دُوِّرت** إلى سرّ عشوائي وسُلِّم للمشغّل خاصة
> (التحقق الحي: الكلمة المنشورة القديمة مرفوضة، والدخول الجديد
> يعمل بدور OWNER عبر مسار المصادقة الفعلي). حساب هوية المشغّل
> بانتظار بريده المتحقّق — انظر
> [جاهزية الإطلاق §3](launch-readiness.md#3-حساب-المالك-حالة-تجهيز-المشغّل).

### 5) أهداف RPO/RTO ومتى تجوز الاستعادة الحيّة (r182 — المرحلة 9)

> «استراتيجية النسخ»: الكوارتز منها وظيفة المالك (Neon) — المنصة
> تجهّز المسار ونقيسه (سكربتات + تجربة محلية مُسجّلة). الأرقام أدناه
> **أهداف معلنة** لوضعَي التشغيل الحاليين، لا نتائج مقيسة بعد:

| الوضع | RPO المستهدف | RTO المستهدف | المسار |
|---|---|---|---|
| المعاينة العامة (الحالي) | ≤ 7 أيام | ≤ 24 ساعة | نسخة يدوية دورية (r166c) + نسخ Neon الذاتية بحسب خطة مشروعك — لا تفترض نافذة معينة دون التحقق من لوحة Neon (Settings/Backups) |
| الطيار المؤسسي (5–10 طلبة) | ≤ 24 ساعة | ≤ 4 ساعات ضمن ساعات العمل | نسخة يومية يدوية قبل يوم الدراسة + Neon PITR إن كانت الخطة تدعمها + تنفيذ قائمة §3 المُجرّبة محليًا (مدخل 1 في سجل التجارب) |

**متى تجوز الاستعادة فوق قاعدة الإنتاج الحيّة؟** بترتيب صارم:

1. **لا تُنفَّذ أبدًا** كخطوة تشخيص أو تجربة — التجربة تخصّص فرعًا
   جديدًا (قائمة §3).
2. تجوز فقط كفعل إنقاذ واعٍ بعد: (أ) تعذّر إصلاح البيانات بالمسارات
   العادية، (ب) استعادة على فرع معزول ناجحة ومتحقَّق منها أولًا،
   (ج) قرار المالك الموثّق بتاريخه وسببه، (د) تمرير
   `--confirm-live-restore` الصريح لسكربت `db:restore` (الحارس
   المزدوج اللغتين يشرح المسار الآمن عند الرفض).
3. **التراجع الكودي لا يلمس البيانات أبدًا** (Rollback أعلاه) —
   التراجعان مختلفان عمدًا ولا يُخلط بينهما.
4. بعد أي استعادة حيّة: `npm run smoke` + فحص لوحة المالك قبل
   إعادة فتح الوصول، وتوثيق الحادثة هنا وفي
   `docs/runbooks/restore-exercise-log.md`.

### 6) ما لا يغطيه هذا الدليل

- ملفات الرفعات (PDF) ليست في القاعدة — تُدار من لوحة حاوية S3/R2
  إن ضُبط السائق (قسم «تخزين رفعات PDF في الإنتاج» أدناه).
- الجدولة (كل كم مرة؟) والتخزين خارج الموقع مسؤولية المالك — المنصة
  لا تدير دورة نسخ احتياطي داخل التطبيق.

## قيود بيئة النشر (اعرفها قبل أي ميزة جديدة)

- **قرص زائل والرفعات حقيقية الآن**: رفعات PDF (أوراق البحث + مواد
  المقرر) منفَّذة خلف تجريد التخزين (`backend/src/lib/storage.ts`)، والسائق
  الافتراضي محلي — أي أن الملفات المرفوعة **تضيع بإعادة النشر/الإقلاع**
  (يسجَّل تحذير إقلاع واحد صريح بهذا المعنى). لدوام الملفات ثلاثة خيارات
  موثقة: `STORAGE_DRIVER=postgres` (r175 — وضع الطيار المحدود أدناه، بلا
  أي كلفة أو بنية إضافية)، أو `STORAGE_DRIVER=s3` + متغيرات `S3_*`
  (الخطوات أدناه)، أو وصل قرص دائم (`disk:`) على خطة مدفوعة — موثق داخل
  `render.yaml` أيضًا.
- خطة مجانية: إيقاف زمني عند الخمول (بداية Neon الباردة يصطف معها
  مهلة 5 ثوانٍ في `/health`)، **ولا تدعم أقراصًا دائمة** — لهذا وُجد
  سائق `postgres` (r175).
- `NODE_VERSION` **مثبتة الآن** على `'22'` في `render.yaml` (r164-l —
  مطابقة لـCI و`engines`؛ أُغلق بند [16](16-decisions-and-limitations.md)
  بالمصدر نفسه).

## تخزين رفعات PDF في الإنتاج (خطوات المالك — مرة واحدة)

قرص Render زائل: مع السائق المحلي الافتراضي تضيع الملفات المرفوعة بإعادة
كل نشر (الخلفية تسجّل تحذير إقلاع واحدًا صريحًا بذلك). دوام الملفات =
تخزين كائنات S3-متوافق (أو وضع `postgres` التجريبي أدناه). الخطوات
الدقيقة (مثال Cloudflare R2 — الأرخص للخطة المجانية؛ AWS S3 / MinIO
بنفس المعادلة):

1. أنشئ حاوية (bucket) — مثل `madarek-files` — وفعّل الوصول للكائنات فقط
   (لا استضافة عامة: كل تقديم يمر عبر الخلفية المصرَّدة).
2. أنشئ رمز وصول API (Access Key ID + Secret) بصلاحيات على تلك الحاوية
   فقط — لا مفاتيح الحساب كاملة.
3. في Render → Environment أضف المتغيرات:
   - `STORAGE_DRIVER=s3`
   - `S3_ENDPOINT=https://<ACCOUNT_ID>.r2.cloudflarestorage.com` — انسخه
     من لوحة R2 (عنونة path-style)؛ مع MinIO عنوان خدمتك، ومع AWS S3
     إقليمك مثل `https://s3.us-east-1.amazonaws.com`
   - `S3_REGION=auto` (اصطلاح R2؛ `us-east-1` مع AWS)
   - `S3_BUCKET=madarek-files`
   - `S3_ACCESS_KEY_ID=…` و`S3_SECRET_ACCESS_KEY=…` (سريّان — Render
     فقط، لا يوضعان في الشيفرة أو `.env.example` بقيم حقيقية)
4. احفظ → autoDeploy يعيد النشر، وتفحص السجلات: لا تحذير القرص الزائل،
   ولا رسالة «STORAGE_DRIVER=s3 requires: …» (تعني متغيرًا ناقصًا —
   `env.ts` يمنع الإقلاع أصلاً حتى تكتمل).
5. تحقق: ارفع ورقة بحث من حساب طالب تجريبي ثم افتح الملف — إن كان يعمل
   فالبايتات في الحاوية (تحقق من لوحة الحاوية إن أحببت).
6. تحقّق مستمر (r167): بطاقة «تخزين الرفعات (PDF)» في صفحة «النظام
   والتشغيل» تعرض حالة الوصول الفعلية للمخزن — حقل `reachable` من
   `GET /owner/system`، فحص memoized كل 60 ثانية بمهلة سباق قصيرة (لا
   يبطئ الصفحة أبدًا). «دائمة» الخضراء تعني أن المخزن أجاب الفحص فعلًا؛
   «مهيَّأ لكن يتعذّر الوصول الآن» الحمراء تعني أن الرفعات الجديدة ستفشل حتى
   يعود — راجع متغيّرات `S3_*` وحالة المزوّد.

## وضع `postgres` (r175) — دوام تجريبي بلا بنية إضافية

لخطة Render المجانية (لا أقراصًا دائمة تدعمها) ولفترة الطيار المحدود
(5–10 طلبة) يوفّر `STORAGE_DRIVER=postgres` دوامًا حقيقيًا بلا أي كلفة أو
خدمة جديدة:

- في Render → Environment أضف متغيرًا واحدًا: `STORAGE_DRIVER=postgres`
  (لا شيء آخر — السائق يستعمل `DATABASE_URL` نفسها وترحيل
  `20261016190858_postgres_binary_objects` يطبَّق تلقائيًا أثناء البناء).
- البايتات تُخزَّن صفوف BYTEA في جدول `BinaryObject` بالمفاتيح القانونية
  نفسها (`papers/` و`materials/`) — بوابات الملكية/التسجيل/الإشراف ونطاقات
  الطلب ودوام حدود الـ20MB والحصص كلها كما هي.
- تحقق: ارفع ملفًا ثم أعد النشر (أو راقب إعادة إقلاع) وافتح الملف مرة
  أخرى — يُقدَّم من القاعدة. تسجَّل في الإقلاع ملاحظة صريحة بأن هذا وضع
  الطيار (توسّع إلى `s3` قبل أي استخدام واسع).
- المقايضة بصدق: البايتات داخل قاعدة التطبيق الأولية (Neon) — مناسب
  لحجم طيار محدود، وليس معمارية مخزن كائنات. راقب حجم الجدول عند التوسّع
  وخطط للانتقال إلى `s3`.

البذور/الترحيلات لا علاقة لها بهذا — الكائنات تُدار من لوحة الحاوية
(النسخ الاحتياطي لأدواتها).

> دليل التحقق الآلي (r167): بروتوكول S3 نفسه يُختبر فعليًا في
> `backend/tests/modules/storage-s3-live.test.ts` — يقلع خادم s3rver حقيقيًا
> في CI (اعتمادية تطوير فقط، لا تُشحن للإنتاج) ويقود السائق عبر المصنع
> الحقيقي: رحلة put/stat/get متطابقة البايتات، `Range` → 206 مع
> `Content-Range`، 404 للمفتاح المفقود، 416 للنطاق غير القابل للتحقيق،
> بقاء `content-type: application/pdf`، ومسبار `probeStorage` — بما في ذلك
> رفض 403 لمفتاح وصول غير مسجّل (فحسبها `reachable: false`). الحدّ الصادق:
> s3rver 3.7.1 لا يتحقق من صحة حساب توقيع SigV4 نفسه (يفحص وجود مفتاح
> مسجّل فقط) — صحّة التوقيع تبقى مثبتة بالمتجه الثابت
> `storage-sigv4.test.ts` + فحص الرفع اليدوي أعلاه (الخطوة 5) لدى المالك.

## تشغيل المساعد الذكي بنموذج حقيقي (خطوات المالك — اختيارية)

الافتراضي محلي (تأليف واعٍ بالإتقان، بلا تكلفة ولا استدعاءات خارجية).
لتشغيل نموذج لغوي حقيقي (أي خدمة متوافقة مع OpenAI: OpenAI نفسها،
Groq، OpenRouter، DeepSeek، Together، vLLM/Ollama ذاتي الاستضافة):

1. أنشئ مفتاح API لدى المزوّد — يُفضَّل مفتاح بميزانية محدودة (الخدمة
   تحدّد الطلب بـ20 طلبًا/دقيقة/مستخدم و800 توكن إخراج للرد الواحد،
   لكن مسؤولية السقف المالي للمفتاح على المالك).
2. اختر اسم النموذج من لوحة المزوّد (مثل `gpt-4o-mini` أو مكافئه
   الرخيص لدى Groq/DeepSeek — ردود دراسيّة قصيرة لا تحتاج نموذجًا
   ضخمًا).
3. في Render → Environment أضف:
   - `AI_PROVIDER=openai`
   - `AI_API_KEY=…` (سري — Render فقط، لا يوضع في الشيفرة)
   - `AI_MODEL=…`
   - `AI_BASE_URL` فقط لو المزوّد ليس OpenAI نفسها (مثل
     `https://api.groq.com/openai/v1` أو عنوان خادم vLLM/Ollama)
4. احفظ → autoDeploy يعيد النشر. إن ظهرت رسالة
   «AI_PROVIDER=openai requires: …» فمتغير ناقص — `env.ts` يمنع
   الإقلاع حتى يكتمل.
5. تحقق: افتح صفحة «المساعد الذكيّ» — الشارة تعرض اسم النموذج
   (والعنوان يقول «مدعوم بنموذج لغويّ حقيقيّ»)، ثم اسأل سؤالًا وانتظر
   الرد. فشل المزوّد يظهر خطأً صادقًا مع زر إعادة محاولة — عمدًا لا
   fallback قالبيًا صامتًا.

## علاقة النشر بالمنظومة

مدارك لا يعتمد على أي خدمة خارجية وقت التشغيل افتراضيًا (لا بريد، لا
Redis؛ المساعد الذكيّ محلي ما لم يفعّل المالك `AI_PROVIDER=openai`
بمزوّد حقيقي — والتخزين محلي ما لم يفعّل `s3`) — قاعدة البيانات هي
الاعتماد الخارجي الوحيد افتراضيًا، مما يجعل النشر
قابلًا للتكرار على أي استضافة Node بنفس المعادلة (بناء + ترحيل + إقلاع).
