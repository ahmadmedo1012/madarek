## Seed-data caveats (read before pairing these into pages)

1. **CT301's lecture videos are dead** (`videoUrl` points off-platform / `example.invalid`): the first course page
   (تقنيات الحاسوب) renders the player in error state "تعذّر تحميل الفيديو". The REAL local videos are only the 3
   SE301 files (`frontend/public/lectures/se301-0*.mp4`, generated by `scripts/lecture-video/`). The
   `lecture-checkpoint` shot therefore uses SE301 lecture 1 (video 9:58, checkpoint at 3:20). If a marketing page
   needs a CT301 lecture frame, the seed must first get local videos for it.
2. **AI tutor runs in honest local-composer mode** (no external provider in the sandbox): `GET /ai/config → provider: "local"`.
   The exchange in the shot is real (user question + platform-generated reply, persisted as a conversation), but the
   reply is the local analyzer's — not an LLM. The page itself labels this honestly ("مساعد تحليليّ محليّ").
3. **Owner dashboard renders airy** (std≈17 luminance): the R333 owner shell is a light, low-density surface —
   the shot contains real live KPIs (verified via innerText) but reads quieter than Heron's dense app windows.
   Same for student-dashboard. If ING wants denser marketing frames, the exam taker (`exam-active.webp`) and
   lecture player are the densest shots we have.
4. Exam shot is the **start gate + active taker with a running timer**; the timer screenshot was taken ~5s into
   attempt 1 of the seeded short exam (5 questions) — the attempt stays IN_PROGRESS in the dev DB afterwards.
5. Login rate limiter is real (10/15min/IP): each capture run logs in once per role (3 total). The capture scripts
   reuse the UI form (`#auth-email`/`#auth-password`) so cookie + zustand `mdrk-auth` state are exactly what the
   app sets; no token was written to any committed file.

## Dev-env gotchas discovered (for the lead / next media tasks)

- **`fs.inotify.max_user_watches=8192` is exhausted in the sandbox** (orphan vite daemons hold the budget). When the
  OwnerPages lazy chunk pulls its large component tree, vite's FSWatcher dies with `ENOSPC` and every request for that
  chunk 504s ("Outdated Optimize Dep") until boot. Owner shots only work with a polling watcher:
  `npx vite --port 5201 --config /tmp/vite.poll.config.mjs` where the temp config merges the repo config and sets
  `server.watch.usePolling=true`. A `dev-once.sh` variant flag (or `optimizeDeps.include` + polling in the repo vite
  config) would make owner captures reproducible.
- `dev-once.sh` runs vite with `--force`; the dep re-optimization race can 404 lazily-imported chunks on the FIRST
  browser visit of a fresh boot (symptom: `Failed to fetch dynamically imported module …` + the
  "تعذّر تحميل هذا القسم" boundary). The capture scripts reload-until-mounted.
- An orphan vite on :5199 survived across sandbox calls and serves stale transforms; a sibling session appears to be
  using it. Use fresh ports (5201+) and kill only your own pids.
