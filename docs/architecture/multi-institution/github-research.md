# بحث المصادر — التعدّد المؤسسي (المرحلة 1)

> وثيقة المرحلة 1 من خطة تحوّل مدارك لمنصّة تخدم مؤسسات تعليمية متعددة.
> كل رابط أدناه **تم فتحه فعليًا** أثناء البحث (2026-10-17)، والنتائج
> المذكورة مبنية على محتوى الصفحات/المستودعات كما وُجدت، لا على أوصاف
> ثانوية. الترخيص حالة مدروسة لكل مرشّح — العام لا يعني مفتوح المصدر.

## 1. المرشّحون الذين فُحصوا

### 1.1 Vercel Platforms Starter Kit

- **الرابط المفتوح:** `https://github.com/vercel/platforms` (README الخام
  عبر raw.githubusercontent.com + واجهة الـAPI للمستودع + شجرة الملفات).
- **الحالة (كما وُجدت):** نشِط (آخر دفع 2026-07-08)، ~6.7k نجمة، **37
  ملفًا فقط**، غير مؤرشف.
- **الترخيص:** **لا يوجد ملف ترخيص إطلاقًا** (واجهة الـAPI تُرجع
  `license: None`؛ طلبُ `LICENSE` من raw يعيد 404). هذا يعني «جميع
  الحقوق محفوظة» افتراضيًا — **نسخ أي شيفرة منه غير مسموح**، واقتصار
  الاستفادة على المفاهيم فقط.
- **المعمارية الفعلية الحالية:** Next.js 16 + App Router + **Upstash
  Redis** كمخزن بيانات المستأجرين (مفاتيح باسم المستأجر)، ولوحة إدارة،
  وتوجيه نطاقات فرعية لكل مستأجر. **لا يوجد Prisma ولا PostgreSQL** في
  المستودع بعد إعادة بنائه (طلب `prisma/schema.prisma` يعيد 404).
- **ما يمكن استلهامه:** نمط «حلّ سياق المستأجر قبل أي عرض» (subdomain →
  tenant lookup → 404 عند غيابه)، وفكرة لوحة إدارة منفصلة للمستأجرين.
- **عدم التوافق مع مدارك:** نمط تخزين Redis بلا سلامة علائقية (مدارك
  علاقي بالكامل مع FKs وقيود فريدة)؛ النطاقات الفرعية خارج نطاق المرحلة
  1 (قرار منتج صريح)؛ لا ترخيص؛ منتج عرض Next.js خالص مقابل Express+SPA.
- **التوصية:** مرجع مفاهيمي فقط، **صفر اعتماد شيفرة**.

### 1.2 PostgreSQL Row-Level Security (الوثائق الرسمية)

- **الرابط المفتوح:** `https://www.postgresql.org/docs/current/ddl-rowsecurity.html`
  (نسخة PostgreSQL 18 — فُتحت الصفحة كاملة).
- **الحقائق المؤثرة على قرار مدارك:**
  - السياسات لكل أمر (SELECT/INSERT/UPDATE/DELETE/ALL) ولكل دور.
  - عند تمكين RLS بلا أي سياسة: **رفض افتراضي** (default-deny).
  - **مالك الجدول لا تخضع صفوفه للسياسات افتراضيًا** — يلزم
    `FORCE ROW LEVEL SECURITY` أو دور اتصال غير مالك (وهو الشرط العملي
    لفرض RLS من تطبيق يملك الجداول).
  - `TRUNCATE` و`REFERENCES` خارج نطاق RLS.
  - دوال leakproof وحدها قد تُقيَّم قبل شرط المستخدم.
  - تجاوز BYPASSRLS/الـsuperuser واقع يجب تصميم الدور حوله.
- **الاستنتاج لمدارك:** RLS **طبقة دفاع ثانية محتملة** لا أساس العزل —
  لأن فرضه الفعلي يتطلب دور اتصال مخصّصًا لكل طلب/جلسة مع `SET
  app.institution_id`، وPrisma لا يدعم رسميًا تمرير `SET` على نفس اتصال
  الطلب (انظر 1.4).

### 1.3 Moodle Workplace — Multi-tenancy

- **الرابط:** `https://docs.moodle.org/502/en/Multi-tenancy` — **تعذّر
  فتحه مباشرة** (جدار Cloudflare يطلب تحدي JS). اعتُمدت نتائج البحث
  المؤرَّخة (2026-05) عن الصفحة نفسها كمرجع.
- **الحقائق المقتبسة من مقتطفات الصفحة:** كل بيانات المستأجرين تُخزَّن
  في **نفس قاعدة البيانات والجداول**، وبشكل افتراضي لا تُشارك البيانات
  الشخصية بين المستأجرين؛ العزل بمستوى التطبيق عبر عمود المستأجر وتراتب
  تكلفة/مجموعات المستأجرين (Workplace ميزة تجارية مدفوعة).
- **الاستنتاج لمدارك:** أكبر منصة LMS تعليمية في العالم اختارت «قاعدة
  مشتركة + عزل على مستوى التطبيق» لنفس حجم الاستخدام المستهدف — يؤكد
  الخيار 1 (انظر architecture-decisions.md §3). لا شيفرة قابلة
  للاعتماد (منتج مغلق تجاري).

### 1.4 Prisma — القيود المعروفة متعددة المستأجرين

- **Issue #5128** «Supporting session-dependent queries like Postgres'
  SET across queries of a request» — **مفتوح** (78 تعليقًا) عند الفتح:
  Prisma لا يضمن تنفيذ `SET` و`findMany` على **نفس** الاتصال من الـpool
  — أي أن سِياق RLS للجلسة لا يمكن ضبطه بطريقة مدعومة عبر Prisma Client.
- **Issue #12420** «Isolating multi-tenant data via database schemas» —
  مفتوح كطلب ميزة: عزل schema-per-tenant عبر Prisma غير مدعوم رسميًا
  (يتطلب PrismaClient لكل مستأجر مع تبديل search_path يدويًا).
- **دليل ZenStack (مارس 2023، Jiasheng):** مقارنة صريحة للمقاربات
  الثلاث مع الحِِجج العملية: DB-per-tenant (أعلى عزل، عبء تشغيلي قاتل
  عند التوسع، مشاركة البيانات العابرة للمستأجرين مؤلمة)؛ schema-per-tenant
  (وسط)؛ قاعدة واحدة + tenantId (الأنسب للـSMB و«عندما لا تستطيع تخصيص
  فريق لإدارة القواعد») — مع تحذير صريح من الاعتماد على Prisma
  middleware كحد أمني لأن **عوامل التصفية العلائقية لا تمر عبر
  الـmiddleware** (issue #3398).
- **الاستنتاج لمدارك:** المرشّح العملي = قاعدة مشتركة + `institutionId`
  صريح + تفويض على مستوى التطبيق (نمط موجود أصلًا في مدارك:
  `buildScopedUserWhere` و`lib/permissions.ts`)، مع دراسة RLS لاحقًا
  كطبقة ثانية لأدق الجداول.

### 1.5 BoxyHQ SaaS Starter Kit

- **الرابط المفتوح:** `https://github.com/boxyhq/saas-starter-kit`
  (README الخام + `prisma/schema.prisma` الخام + واجهة الـAPI).
- **الحالة:** نشِط (2026-07-20)، ~5k نجمة.
- **الترخيص:** **Apache-2.0** (مسموح استلهام/نسخ مع الإبقاء على
  الإشعارات — لكن مدارك احتكاري والاعتماد المباشر غير مطلوب).
- **نموذج العزل:** `User` عالمي + `Team` (المستأجر) + **`TeamMember`
  (teamId, userId, role — دور لكل عضوية)** + `Invitation` — على
  Prisma/PostgreSQL بقاعدة مشتركة و`teamId` في جداول المحتوى.
- **ما يُستفاد منه مباشرة مفاهيميًا:** نموذج «الدور داخل العضوية لا
  داخل المستخدم» و«دعوة العضوية برمز» — وهو جوهر قرار العضوية في
  مدارك (§4 من architecture-decisions.md).
- **عدم التوافق:** مبنى Next.js/NextAuth بالكامل (مدارك Express+JWT)،
  ومحمل بميزات خارج نطاقنا (SAML/SCIM/Stripe/Retraced).

### 1.6 cal.com (اليوم cal.diy)

- **الرابط المفتوح:** واجهة الـAPI لـ`calcom/cal.com` (يعيد التوجيه إلى
  `calcom/cal.diy`) + فحص ملف LICENSE.
- **الحالة:** نشِط (2026-09-26)، ~49k نجمة.
- **الترخيص الحالي للـrepo كما ورد من الـAPI:** **MIT** (تحقق مباشر من
  الـAPI؛ مع التنبيه أن تاريخ الترخيص تغيّر عبر الزمن — استخدام الشيفرة
  يتطلب إعادة تحقق لحظيًا قبل أي اعتماد فعلي).
- **العلاقة بالبحث:** هو المرجع الذي يستشهد به دليل ZenStack لتطبيق
  «قاعدة واحدة + teamId + تفويض تطبيقي» على Prisma بتعقيد أعلى من مدارك.
- **الاستفادة:** نمط جداول العضوية المتعددة والتمييز بين بيانات
  المستخدم العالمية وبيانات الفريق. لا حاجة لنسخ شيفرة.

## 2. خلاصة عملية للمرحلة 1

| المرشّح | ترخيص | صيانة | قابلية الاستلهام | قرار |
|---|---|---|---|---|
| Vercel Platforms | **بلا ترخيص** | نشِط | مفاهيم توجيه المستأجر فقط | مرجع مفاهيمي، صفر شيفرة |
| PostgreSQL RLS (رسمي) | — (وثائق) | — | سياسات صفية كطبقة ثانية | مؤجل لما بعد المرحلة 2 مع دور اتصال مخصّص |
| Moodle Workplace | تجاري مغلق | — | تحكيم نمط «قاعدة مشتركة» | تأكيد الخيار 1 |
| Prisma #5128/#12420 | — (Issues) | — | قيود رسمية موثقة | يرجّح tenantId صريحًا لا RLS/ولا schema-per-tenant |
| ZenStack guide | محتوى مدونة | 2023 | حِجج المقاربات الثلاث | مرجع التحكيم |
| BoxyHQ SaaS Kit | Apache-2.0 | نشِط | نموذج العضوية/الدور-لكل-عضوية | استلهام النموذج فقط |
| cal.com/cal.diy | MIT (تحقق لحظي قبل الاستخدام) | نشِط | مرجع النمط على Prisma | استلهام فقط |

**القرار المستخلص (يفصّله architecture-decisions.md):** قاعدة PostgreSQL
واحدة مشتركة مع `institutionId` صريح على الجداول المؤسسية، ونموذج عضوية
بواقع دور لكل عضوية على غرار TeamMember (BoxyHQ) — مع إبقاء RLS
PostgreSQL خيارًا مؤجلًا لطبقة دفاع ثانية بعد إثبات جدواه بتصميم دور
الاتصال (قيود Prisma #5128 موثقة أعلاه).
